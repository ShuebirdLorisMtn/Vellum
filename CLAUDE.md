# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Vellum is a Node.js/Express backend (plus a static, vanilla-JS frontend) for a self-learning AI document-generation product: Claude API generation, Supabase for auth/database/real-time sync, Stripe + Whop for payments, a free-tier paywall, viral read-only share links, and a feedback-driven "gene weight" learning engine. Plain CommonJS, no build step, no linter, no test framework.

## Commands

```bash
npm install
npm start          # node src/server.js (port 3000, override with PORT)
npm run dev        # nodemon, restarts on src/ changes
```

There is no test suite. The only test tooling is a manual webhook script:

```bash
WHOP_WEBHOOK_SECRET=... WEBHOOK_URL=http://localhost:3000/webhooks/whop node scripts/test-whop-webhook.js
```

Configuration comes from a `.env` file (loaded via dotenv) — copy `.env.example` and fill in `CLAUDE_API_KEY`, `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, `STRIPE_PRICE_MONTHLY`, `STRIPE_PRICE_YEARLY`, `WHOP_WEBHOOK_SECRET`, `WHOP_PRODUCT_URL`, `APP_BASE_URL`. The server boots and serves the frontend with nothing configured; endpoints that need Supabase return 503 (`backend_not_configured`) and Stripe checkout returns 503 (`stripe_not_configured`) until those are set.

## Architecture

There is no application database of our own — **Supabase is the database, auth provider, and real-time layer**. The Express app is a thin layer that (a) holds secrets Supabase RLS can't gate (the Claude API key, Stripe secret key, service-role key) and (b) does the Claude generation call. Everything else — reading the user's profile, reading/writing their document Vault, reading global gene weights, submitting feedback — the frontend does by talking to Supabase directly with the anon key, protected by Row Level Security policies.

- **`supabase/schema.sql`** — the source of truth for the schema. Run it once in the Supabase SQL editor (or `supabase db push`). It's idempotent (safe to re-run) and defines:
  - `profiles` (1:1 with `auth.users`, auto-created via a trigger on signup): `free_docs_remaining` (default 3), `subscription_active`, `plan`, `stripe_customer_id`, `docs_generated`, `voiceprint` (jsonb — see Learning engine below).
  - `documents`: `title`, `content`, `tone`, `genes` (text array), `share_id` (random, unique, generated by default), `share_enabled`.
  - `feedback`: one row per thumbs vote, tied to a document.
  - `events`: `copy` / `download` / `regenerate` / `generate` / `share_created` / `share_view` — the last one insertable by **anonymous** visitors (RLS policy requires `user_id is null`), everything else requires the row's `user_id` to match `auth.uid()`.
  - `tone_preferences`: per-user aggregate up/down counts per tone.
  - `gene_weights`: **global**, not per-user — one row per gene (`mirror`, `rosetta`, `arbiter`, `catalyst`, `magna`), readable by anyone, writable only through the RPC below.
  - `record_feedback(document_id, rating, tone, genes)` — a `security definer` RPC that is the *only* way feedback is written. In one transaction it: inserts the `feedback` row, upserts `tone_preferences`, nudges the global `gene_weights` (±0.01/-0.005 per vote, clamped to [0.5, 2.0]), and — once the user has generated 5+ documents — recalculates their `voiceprint` (their historically best-performing tone) and stores it on `profiles`. This is the whole learning flywheel; if you change the learning behavior, change it here, not in application code.
- **`src/supabase.js`** — the server-side Supabase client, built with the **service-role key** (bypasses RLS — never send this key to the browser). Exposes `getUserFromToken` (validates a bearer token from the frontend), profile CRUD, and `saveDocument`. `configured()` gates every backend route that touches Supabase.
- **`src/claude.js`** — `generateFromClaude(apiKey, model, prompt, maxTokens, system)` using the official `@anthropic-ai/sdk`. Default model `claude-opus-5` (override with `CLAUDE_MODEL`). Opts into the server-side refusal-fallback beta for Opus 5 / Fable 5 models and throws a `claude_refused` error on `stop_reason: "refusal"` (surfaced as a 422 from `/api/generate`).
- **`src/app.js`** — the Express app (exported, no `listen` — see Deployment). Routes:
  - `GET /config` — public runtime config for the frontend: `SUPABASE_URL`, `SUPABASE_ANON_KEY` (the anon key is meant to be public; RLS is the security boundary), `WHOP_PRODUCT_URL`, `STRIPE_ENABLED`.
  - `POST /api/generate` (auth required) — the only route that calls Claude. Applies the free-doc/subscription paywall, folds the user's `voiceprint` into the system prompt if they have one, saves the document via the service-role client, and decrements `free_docs_remaining` **only after** a successful generation (a failed Claude call never burns the user's free doc).
  - `POST /api/stripe/checkout` (auth required) — creates a Stripe Checkout session for the `monthly` or `plan` body field (`monthly` | `yearly`), pinned to the user via `client_reference_id` and `metadata.user_id`.
  - `POST /webhooks/stripe` — verifies `stripe-signature` against the raw body (captured by the `express.json` `verify` hook for any `/webhooks/*` path) and sets `subscription_active` on `checkout.session.completed` / clears it on `customer.subscription.deleted`.
  - `POST /webhooks/whop` — HMAC-SHA256 verification (hex or base64, optional `sha256=` prefix, from `x-whop-signature` or `whop-signature`, `crypto.timingSafeEqual`) is unchanged from before Supabase. On a verified event with a buyer email, finds or creates the Supabase user (`auth.admin.createUser`, which triggers profile creation) and sets `subscription_active = true, plan: 'whop'`. If `WHOP_WEBHOOK_SECRET` is unset, verification is skipped entirely — same as before.
- **`src/server.js`** — thin wrapper: `require('./app').listen(PORT)`, used for local `npm start` only.

### Frontend (`public/index.html`, `public/share.html`)

Vanilla JS, no build step. Loads `@supabase/supabase-js` from a CDN (`unpkg.com/@supabase/supabase-js@2/dist/umd/supabase.js`) and constructs the client from `/config` at load time.

- **Auth** is Supabase Auth magic-link (`signInWithOtp`); there is no custom JWT or `/api/send-magic-link` anymore. Session state comes from `supabase.auth.getSession()` / `onAuthStateChange`; the access token is sent as `Authorization: Bearer` to the two backend routes that need it (`/api/generate`, `/api/stripe/checkout`).
- **The Vault** (document history) is read directly from Supabase (`documents` table, RLS-scoped to the signed-in user) and kept live across tabs/devices via a `postgres_changes` real-time subscription on `INSERT`.
- **Gene weights** are fetched from the public `gene_weights` table on sign-in and used to weight `detectGenes()` client-side — this is how one user's feedback (via the `record_feedback` RPC) subtly shifts document generation for everyone.
- **Feedback** (👍/👎) calls the `record_feedback` RPC directly — the frontend never writes to `feedback`, `tone_preferences`, or `gene_weights` itself.
- **Event tracking** (`copy`, `download`, `regenerate`, `generate`, `share_created`) inserts into `events` directly from the client, scoped to the signed-in user.
- **Share links** (viral loop): "Share" sets `documents.share_enabled = true` (an RLS-permitted update on your own row) and copies `${origin}/s/${share_id}`. `/s/*` is a Netlify redirect (see `netlify.toml`) to `public/share.html`, a separate static page that reads the id from the URL path, fetches the document anonymously (RLS policy: anyone may `select` a row where `share_enabled = true`), renders it read-only with a "Made with Vellum" badge and a "Create your own free document" CTA back to `/`, and logs an anonymous `share_view` event.

## Deployment

**Netlify (active):** the site `vellum-docs-app` (https://vellum-docs-app.netlify.app) serves `public/` as static assets and runs the Express app as a serverless function. `netlify/functions/api.js` wraps `src/app.js` with `serverless-http`; `netlify.toml` rewrites `/api/*`, `/webhooks/*`, `/config`, and `/health` to the function, and `/s/*` to `public/share.html` (a real static file, not the function). Keep new dynamic routes covered by those redirects. Test locally with `netlify dev --offline` (port 8888) — `npm start` (plain Express on port 3000) does **not** apply the `/s/*` rewrite, since that's Netlify-only routing. Deploys are pushed via the Netlify MCP `deploy-site` flow, not git-linked CI.

**Azure (dormant):** `.github/workflows/azure-webapps-node.yml` deploys to an Azure Web App on push to `main` (Node 20). It requires `AZURE_WEBAPP_NAME` in the workflow (currently the `your-app-name` placeholder) and the `AZURE_WEBAPP_PUBLISH_PROFILE` repo secret — it fails until those are configured or the workflow is removed.

## Setting up a fresh Supabase project

1. Create a project at supabase.com, then run `supabase/schema.sql` in the SQL editor.
2. Project Settings → API: copy the Project URL (`SUPABASE_URL`), `anon` `public` key (`SUPABASE_ANON_KEY`), and `service_role` `secret` key (`SUPABASE_SERVICE_ROLE_KEY` — server-side only, never in frontend code or `/config`).
3. Authentication → URL Configuration: set the Site URL to `APP_BASE_URL` so magic-link redirects land back on the app.
4. Authentication → Providers → Email: magic link (OTP) is on by default; no separate email provider (e.g. SendGrid) is needed — Supabase sends the emails.
